# Contributing

Thanks for taking a look. Spoor is small on purpose: one Python package, no framework, no build
step for the dashboard, and a test suite that runs in under a minute.

## Run it from a checkout

```bash
pip install -r requirements.txt       # the same pinned libraries the Windows package bundles
./spoor.sh selftest                   # Linux / WSL / macOS: the built-in self-test on the fictional demo returns
python tests/run_tests.py             # units + self-test + dashboard/API and security checks
```

On Windows without a Python install, build the package instead (`build/fetch_deps.py`, then
`build/package.py`) and run `SELFTEST.bat` from the unpacked ZIP.

## Ground rules

* **Fictional test data only.** Everything under `demo/` is generated by `tests/make_demo_data.py`
  from documentation IP ranges and invented names. Never add a real return, a real identifier or a
  real person's data, even redacted.
* **Every statement cites.** A new analysis must produce findings whose evidence rows cite the
  source, line/row/page and, where used, the pairing method, and `tests/run_tests.py` must still
  pass the citation check. Findings without citations are rejected by design.
* **No new network calls.** The air-gap property is the point of the tool.
* **Keep the model honest.** Anything the model writes goes through `verify.py`; do not add a path
  that shows model output to the examiner without verification against cited findings.
* **Pin dependencies** in both `requirements.txt` and `build/requirements-vendor.txt` (with hashes),
  and add the license text to `LICENSES/`.

## Pull requests

One change per PR, with a test when the change is testable, and a line in `CHANGELOG.md`. Mention
how you tested on Windows if the change touches the launchers, paths or the dashboard.
